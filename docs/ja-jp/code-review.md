# コードレビュー・ガイドライン
## はじめに
ソフトウェアのコードレビューは、コードが機能要件を満たしているかを確認し、開発者がベストプラクティスに従うのを助けるプロセスです。さらに、コードレビューはソフトウェア品質の向上にも役立ちます。


## 基本的なコードレビュー・チェックリスト

レビュー中は、次の基本的な質問を自分に投げかけてください。

- コードを容易に「理解」できますか？
- コードは「コーディング規約/ガイドライン」に従って書かれていますか？
- 同じコードが2回以上「重複」していませんか？
- 根本原因を見つけるために「ユニットテスト/デバッグ」しやすいですか？
- この関数やクラスは「大きすぎ」ませんか？もし大きいなら、責務を持ちすぎていませんか？

上記のいずれかに満足のいく回答ができない場合は、コード変更を提案/推奨してください。


## 詳細なコードレビュー・チェックリスト
以下のチェックリストは、レビュー時に考慮すべき観点の例です。

![コードレビュー・チェックリスト - Expert Code Reviewer](_media/Experienced-Code-Reviewer.webp)

### 1. コード整形（フォーマット）
コードを読み進める際、可読性向上とブロッカー排除のため、整形を確認します。

- 左寄せ、適切な空白の使用。ブロックの開始/終了が識別しやすいこと。
- 命名規則（Pascal, camelCase 等）が守られていること。
- コードは標準的な14インチ画面に収まること。横スクロールが不要であること。21インチ等の広い画面ではツールウィンドウを開いた状態でも編集できることを意識する。
- コメントアウトされたコードは削除すること。必要であればソース管理（例: Git）から取得できます。

### 2. アーキテクチャ
定義されたアーキテクチャに従っていること。

- 関心の分離（Separation of Concerns）が守られていること。
  - 要件に応じて適切に層/レイヤへ分割（Presentation, Business, Data 等）。
  - HTML / JavaScript / CSS などは適切にファイルを分割。
- 既存のコードパターン/技術と整合していること。
- デザインパターン: 問題と文脈を理解した上で適切なパターンを採用。

### 3. コーディングのベストプラクティス
- ハードコーディングを避け、定数/設定値を用いる。
- 類似の値は列挙型（enum）などにまとめる。
- コメントは「何をしているか」ではなく「なぜそうしているか」を記載。ハック、ワークアラウンド、一時的な修正、未完タスク（TODO）などを明確に。
- 多重の if/else ブロックは避ける。
- 可能な限りフレームワークの機能を使い、車輪の再発明を避ける。

### 4. 非機能要件
- 保守性（サポート容易性）: 近い将来に最小の労力でサポートでき、欠陥の特定・修正が容易であること。
  - 可読性: コードは自己説明的であること。変数名、関数名、クラス名は分かりやすく。理解に時間がかかるなら、リファクタかコメントの追加を検討。
  - テスト容易性: テストしやすい構造であること。必要に応じて関数へ切り出す。別レイヤとやり取りする際はインターフェースを用いてモックしやすく。static 関数やシングルトンはモックが難しいため避ける。
  - デバッグ容易性: フローや引数、例外情報を記録できるようにし、根本原因を追いやすく。ログの永続化先（DB など）も検討。
  - 設定容易性: 値が頻繁に変わるものはコードではなく設定（ファイル/DB）で切り替え可能に。
- 再利用性
  - DRY（Don't Repeat Yourself）を徹底し、同じコードを3度以上繰り返さない。
  - 再利用可能なサービス/関数/コンポーネントを検討。
  - 汎用的な関数/クラスの設計を検討。
- 信頼性: 例外処理とリソースのクリーンアップ（解放）。
- 拡張性: 既存コードの変更を最小限にして機能拡張できること。コンポーネントの差し替え容易性。
- セキュリティ: 認証/認可、入力値の検証、SQLインジェクションやXSS対策、機密データの暗号化（パスワード/クレカ情報等）。
- パフォーマンス
  - データ型の選択（例えば StringBuilder, ジェネリックコレクション等）。
  - 遅延読み込み、非同期/並列処理。
  - キャッシュとセッション/アプリケーションデータの活用。
- スケーラビリティ: 大規模ユーザ/データに耐えられるか。Web ファームでの運用可能性。
- ユーザビリティ: ユーザ視点で UI/API が直感的か。納得できない UI であれば提案・議論する。

### 5. オブジェクト指向分析設計（OOAD）原則
- 単一責任の原則（SRP）: 複数の責務を1つのクラス/関数へ詰め込まない。必要に応じて分割。
- オープン/クローズドの原則: 新機能追加の際、既存コードを変更しない。新しいクラス/関数で拡張する。
- リスコフの置換原則: 子クラスは親クラスの振る舞い（意味）を変えない。基底クラスの代替として利用できること。
- インターフェース分離の原則: 冗長なインターフェースではなく、機能ごとに小さなインターフェースへ分割。不必要な依存（引数等）を含めない。
- 依存性の注入: 依存をハードコードせず、注入する。
  多くの場合、これらの原則は相互に関連します。例えば「単一責任の原則」を守ると、再利用性やテスト容易性は自然と高まります。

場合によっては、要件同士が相反することがあります（例: パフォーマンス vs セキュリティ）。多層での過度なチェックやログは性能を下げますが、金融などのアプリケーションでは多層のチェックや監査ログが求められることがあります。文脈に応じて最適なトレードオフを選択してください。

### コードレビューに役立つツール
- プロジェクト全体の品質を俯瞰する第一歩として静的解析ツールを活用します。技術に応じて [SonarQube](http://www.sonarqube.org/), [NDepend](http://www.ndepend.com/), [FxCop](https://en.wikipedia.org/wiki/FxCop) などを検討。
- IDE プラグインの活用（例: [ReSharper](https://www.jetbrains.com/resharper/)）。ベストプラクティスの提案が得られます。
- コードレビューコメントのトラッキングには [Crucible](https://www.atlassian.com/software/crucible/overview), [Bitbucket](https://bitbucket.org/) などのツールを利用。


## コードレビューのコツ

### 1. 問題点を可視化する
開発者にコードの変更を「強制」しないでください。自尊心を傷つける可能性があり、変更理由に納得していないと同じミスを繰り返す恐れがあります。現行コードの問題点とその影響を明確にしましょう。

> “If an egg is broken by outside force, life ends. If broken by inside force, life begins. Great things always begin from inside.” – Jim Kwik

### 2. 関連する原則を説明する
提案に対して開発者が難色を示す場合、[関心の分離](http://en.wikipedia.org/wiki/Separation_of_concerns), [SRP](http://en.wikipedia.org/wiki/Single_responsibility_principle), [Open-Closed 原則](http://en.wikipedia.org/wiki/Open/closed_principle), [循環的複雑度](http://en.wikipedia.org/wiki/Cyclomatic_complexity) など関連原則を説明し、必要に応じて非機能要件（保守性、拡張性、テスト容易性、信頼性）を議論してください。

### 3. 関連する名言を共有する
レビューを興味深く前向きなものにするため、以下のような名言/格言を共有します。

- “Any stupid can write the program that computer understands but only good programmers write code that humans understand” – Martin Fowler
- “Measuring programming progress by lines of code is like measuring aircraft building progress by weight.” – Bill Gates
- “Fat model and thin controller”, “High cohesion and Low coupling”
- “When debugging, novices insert corrective code; experts remove defective code.” – Richard Pattis

### 4. オフラインでできることは進める
逐一席で説明するのではなく、関連情報のリンクやキーワードを共有し、自主的な調査を促してください。レビューアにも開発者にも時間の余裕が生まれます。

また、常に隣でレビューするのではなく、ソース管理からコードを取得してレビューすることで、開発者の手を止めずにすみ、より良い提案を準備する時間も確保できます。

### 5. ベストプラクティスを学ぶ機会にする
時に、レビューコメントを個人的な批判と受け取り、防御的になることがあります。レビューアはこれは学習と議論の機会であると伝え、また、レビューコメントが開発者の評価に直結しないようマネージャーにも周知するのが望ましいです。

### 6. 忍耐強く、必要なら見直す
議論が平行線になる場合、レビューアは文脈や制約を完全には理解していない可能性があります。相手の主張を遮らずに聞き、紙やホワイトボードでアプローチの比較を可視化すると有効です。結論が出なければ「明日、もう少し分析してから話そう」といったクローズも選択肢です。翌日にフレッシュな視点で見直すと新しい解が見つかることがあります。

### 7. ベストプラクティスの必要性を説明する
タイトなスケジュールを理由にベストプラクティスが後回しになることがあります。しかしコード規模が大きくなるほど保守は困難になります。デリバリー後にコードが第三者の目に触れる場合、品質に悪影響を与えかねません。リファクタリングの重要性を説明し、必要な時間の確保をマネージャーと合意しましょう。

### 8. セカンドオピニオンを求める
提案に合意が得られない場合は、第二のレビューアに相談するのも有効です。その結果は最初のレビューアにも共有し、情報の一貫性を保ちます。

### 9. 改善点と技術的負債を記録する
現リリースで対応できない指摘はドキュメント化し、将来の適切なタイミングで対応できるようにします。レビュー時に見つかる改善案は、プロジェクト終盤に探すより効率的です。

### 10. すべてのレビューコメントを文書化する
メール、ドキュメント、スプレッドシート、組織の標準ツールなどにレビューコメントを残します。初回のミスは許容されても、同じミスの再発は避けるべきです。記録は再発防止に役立ち、CMMI プロセスの観点でも有用です。
